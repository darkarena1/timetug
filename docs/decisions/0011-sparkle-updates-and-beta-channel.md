# ADR 0011: Sparkle Updates and a Beta Channel

**Status:** Accepted

## Context

Direct-download users need in-app updates, and people who opt in should get betas of what is merged. Stable releases are Developer-ID-signed and notarized (ADR 0007, 0008). The repository is on GitHub with no server of our own.

## Decision

Use [Sparkle 2](https://sparkle-project.org) for updates, one appcast with a `beta` channel, a beta build on every merge to `master`, and a stable release when the owner cuts a GitHub Release for a `v*` tag.

- **Pin:** Sparkle `exactVersion: 2.10.0` in `Apps/macOS/project.yml`, the same version as `scripts/release/sparkle-version.txt`, which also holds the SHA-256 of the release tarball used for the command-line tools (`sign_update`, `generate_keys`). Bump both together.
- **Feed:** one `appcast.xml` on the `gh-pages` branch, served by GitHub Pages at `https://darkarena1.github.io/timetug/appcast.xml`. Beta items carry `<sparkle:channel>beta</sparkle:channel>`; the app allows that channel only when the user turns on Beta updates. The choice lives in the app's UserDefaults (`updates.includeBetas.v1`). `SUFeedURL` and `SUPublicEDKey` are in `project.yml` `info.properties`. The EdDSA private key is the `SPARKLE_PRIVATE_KEY` Actions secret; a copy is in the owner's keychain.
- **Build number:** `CFBundleVersion` is a UTC timestamp `YYYYMMDDHHMMSS` (14 digits) from `scripts/ci/compute-versions.sh`. Sparkle orders by it, so it must only increase across betas and stable releases. Second resolution makes a beta and a release build-number collision very unlikely, not impossible; `appcast.py` rejects an add with the same `sparkle:version` but a different URL, loudly. Run numbers fail because they are per workflow, and commit hashes have no order. Display versions are labels: `<base>-beta.<timestamp>` for betas, where `<base>` is the newest stable `v*` tag (falling back to `project.yml` when there is none) and `<timestamp>` is the build number.
- **Betas are Developer-ID-signed, not notarized.** Sparkle downloads and installs the update without the quarantine attribute, so Gatekeeper does not assess it. This avoids a notarization round trip per pull request. Stable releases stay notarized.
- **Betas run on merged code only.** Pull requests only run `ci.yml` (build and tests; no secrets, no signing, and nothing that can enter the update feed). `.github/workflows/beta.yml` runs on `workflow_run` of `CI` for `master` pushes that passed (same repository), builds only the tip of `master` (a run for an older commit skips, so re-runs cannot downgrade), skips if the signing secrets are missing, then builds, signs, EdDSA-signs and publishes. The GitHub release is published before the appcast is updated, so the feed never lists an asset that cannot be downloaded. Publishing is serialised with a concurrency group and the newest 5 betas are kept.
- **Stable releases** start from a GitHub Release for a new `v*` tag, in one of two ways. Publishing the release in the UI fires `release: published` and `release.yml` attaches the assets to it. Or the owner saves a draft (drafts fire no release event) and runs `release.yml` manually (`workflow_dispatch` with `tag`), which uploads to the draft and publishes it. There is no tag-push trigger, because publishing creates the tag and would fire both. The workflow builds the tag's commit (on `master`, with approval in the `release` environment), attaches the DMG and Sparkle zip, then adds the appcast item.
- **Immutable releases.** GitHub's immutable-releases setting locks a published release's assets and tag. It was on when `v1.2.0` was published and the workflow failed with `HTTP 422: Cannot upload assets to an immutable release`, burning that tag (published, locked, empty). The owner turned it off. It is currently OFF; if it is turned on again only the draft flow can work, and the workflow fails early (before building) on a published immutable release (`release-state.sh` reports `published-immutable`). A burned tag is never reused: cut a new version.
- **Rejected:** partial (delta or non-bundle) updates, because whole-bundle zips are small enough and much simpler. Per-PR opt-in labels, because they add ceremony and the risk model is the same. Sparkle's `generate_appcast`, because it wants a local folder of archives and rewrites the whole feed; `scripts/release/appcast.py` edits one item at a time under a concurrency group, and is easy to test. Betas built from pull requests (a two-workflow design: an unprivileged build uploads an artifact, a privileged workflow validates and signs it), because it required treating an untrusted artifact carefully (tar validation, extraction outside the workspace, waiting for CI) and any mistake exposes the signing keys to PR authors; building merged code is simpler and safer. Signing in the PR workflow itself, for the same reason.

## Consequences

- The private key is a single point of failure. If it is lost, installed apps cannot verify further updates and users must reinstall manually. Back it up.
- Sparkle adds a framework and XPC helpers to the app bundle; `scripts/release/sign-app.sh` and `sign-and-notarize.sh` sign them inside-out.
- The beta path needs a first real run after merge to confirm that `workflow_run` fires for `CI` on `master` pushes and that the signing secrets are repository-scoped (`beta.yml` has no environment, so secrets kept only in the `release` environment make it skip with a notice).
- A stable release that fails at the appcast step leaves a public release with assets that is not in the feed; the workflow is not idempotent, so recovery is manual (`docs/release.md`). The release is visible without assets for the roughly 30 minutes the build takes.
- The release event checks out `refs/tags/<tag>` (qualified, so a branch named like the tag cannot shadow it) and fails if HEAD is not the tag's commit. A `Validate the tag` step rejects a bad tag before any build or secrets. The real guards for the stable path are the `release` environment approval (deployment policy limited to `master` and `v*` tags) and the tag ruleset; the on-`master` check is a safety net.
- The update UI and Sparkle itself are covered by the manual checklist, not unit tests.
